01 / PROJECT OVERVIEW

Small scope.
Deep systems.

Orynqeth Survivors is a top-down, auto-attacking survival game built around short runs, escalating enemies, meaningful level-up choices, and persistent unlocks.

The project explores how a technical designer can specify interconnected systems, create repeatable editor workflows, and rapidly test gameplay through AI-assisted implementation.

Contribution transparency: I owned design, specifications, balancing decisions, art direction, review, and validation. AI tools produced a substantial portion of the C# code and visual assets under my direction. This portfolio repository contains the website, not the Unity game's source code.

04 / GAME SYSTEMS

Designing for decisions.

Short-run choices, distinct weapon roles, and deliberate difficulty peaks.

COMBAT

Four weapon identities

Magic Bolt is the reliable starting projectile. Orbiting Blades reward positioning, Chain Lightning handles groups, and Meteor delivers delayed area damage.

Distinct targeting, timing and spatial roles
PROGRESSION

Controlled random choices

Each level-up presents three upgrades with at most one weapon option. Rarity weights and Luck influence the quality of offers; tomes expand long-term build direction.

Rarity · Luck · Weapons · Passive tomes
PACING

Escalation and horde waves

Enemy frequency increases throughout a run. Periodic horde events inject sharp pressure spikes into the pacing curve rather than relying on continuous growth alone.

Time-driven density · Event windows
META

Progress beyond one run

Weapons and tomes enter the Collection through unlock conditions. Persistent statistics track completed runs, combat performance and progression across sessions.

Collection · Unlocks · Run history

06 / TECHNICAL DESIGN

Built to be iterated.

Data, lifecycle, and repeatability mattered as much as moment-to-moment combat.

01

Deterministic procedural terrain

Forest tiles and decorations are generated around the camera in reusable chunks. Deterministic placement includes negative world coordinates and chunk boundaries.

9pooled chunks observed
02

Sprite and effect lifecycles

Animation state resets on reuse; projectiles orient to velocity; lightning and meteor visuals follow their damage timing without changing combat rules.

26environment PNG assets
03

Targeted verification

Automated checks cover UI, save isolation, pooling and progression. A reported environment test sampled 1,000 stationary updates and found no managed allocations in that specific loop.

1,000stationary updates sampled

The 1,000-update figure comes from an earlier focused environment check, not a full-game profiler capture. Test methodology and Editor-versus-Player context were not independently verified for this case study; GPU/FPS stress profiling remains undocumented.

07 / CHALLENGES & OUTCOME

Iteration is the work.

01 / BALANCE

One weapon dominated.

Meteor overshadowed other builds. Reviewing the weapon damage breakdown led to stronger alternatives and a more useful starting Magic Bolt.

02 / GAME FEEL

The pacing felt flat.

Continuous enemy scaling alone lacked tension. More frequent spawns and periodic horde waves introduced distinct pressure peaks.

03 / PRODUCTION

Visual regressions slowed progress.

UI overlaps, pooled animation glitches, and screenshot color issues motivated focused validation and repeatable scene captures.

THE RESULT

A playable prototype and a repeatable way to demonstrate it.

The Windows game launches, while Editor tooling can recreate progression states and capture evidence of game systems. The case documents decisions, tools, and iteration — not only a finished screen.
